# Architecture

## Approved foundation

Idlebound targets Android and iOS with a mobile-first 2D Unity client. The editor is pinned to Unity 6.3 LTS `6000.3.26f1`. C# is the gameplay implementation language. Rendering uses the Universal Render Pipeline with its 2D renderer. Git tracks source assets, their metadata, package definitions, and project settings.

Supabase is the planned backend. Its integration is future work: there is no backend client, schema, authentication flow, or cloud persistence implementation in this template. Concrete backend responsibilities and interfaces require approved requirements before implementation. Privileged backend credentials must not be committed or embedded in a distributed client.

Separate development-only CSV catalogs supply gear, monsters, loot and combat tuning; no final combat balance or backend integration is claimed. ## Stage 8B-05 presentation boundary

`GameSessionHost` is the sole Unity session/clock owner. It loads the unchanged catalogs into one `GatheringSession` and registers one engine-independent `SessionRuntime`. The runtime rejects duplicate owners, quantizes absolute realtime into ticks, groups focus/pause absence into a single offline interval and retains the domain's existing eligibility/cap rules. `GameUiModel` projects read-only session state and routes validated commands; navigation/inspection do not settle time or change active selection.

`IdleboundMobileUI`, `MobileUiKit` and `ActivityStage` build the player uGUI experience in `Assets/Scenes/IdleboundPlay.unity`. Existing uGUI/Input System packages are referenced explicitly by the presentation assembly; no new packages are added. `FoundationDevelopmentUI` now reads the same host and delegates explicit debug clock/reset commands, preserving its original scene as a fallback. There is no second gameplay session or settlement loop in either UI. Stage 8B-06 supersedes the original in-memory lifetime: a dedicated persistent host survives scene reloads and opens the validated local player save before live interaction.

Original palette sprites and cosmetic activity projection are replaceable independently of the domain. `CollectionPreview.txt` supplies only approved boss/item identities for unavailable feature shells, not implemented monsters, ownership or effects. Shop transactions, cloud persistence, custom bank organization and full art remain deferred; Stage 8B-06 supplies local persistence and durable offline receipts. See `UIUX.md` and `Stage8B05Verification.md`.


## Stage 8B-06 local durability and offline transaction boundary

`LocalGame` coordinates a version-1 `SaveDocument` through `ILocalSaveStore`; its snapshots contain domain data and stable catalog IDs, never Unity objects or UI copies. `GatheringSession.Capture/Restore` deep-copy and validate roster/access, all nine exact decimal XP/levels, selection, assignments/partials/counters, pending production reservations, inventory, equipment instances/serial, HP/encounters, kill counters, the pure loot seed and scoped background effects. Definitions, item names, computed combat profiles, skill definitions and maximum HP are reconstructed. There is no implemented gold wallet, equipping enchantment power, membership purchase or boss collection ownership to invent/save.

`AtomicLocalSaveStore` writes a checksummed JSON envelope to `Application.persistentDataPath/Idlebound/player-v1.json.tmp`, flushes it, then replaces the primary while retaining `.bak`. First creation also seeds a backup. A failed pre-commit write leaves the previous primary/backup valid. Validated backup recovery quarantines a corrupt primary rather than replacing it with fresh starter state. Future versions, catalog-fingerprint mismatches, inaccessible files or absence of any valid recoverable state block play with Retry and diagnostics; they do not silently start a new game. Hashes detect accidental corruption, not malicious local edits. A changed catalog currently requires explicit migration/review rather than guessed remapping or rebalancing. `link.xml` preserves reflection-based serializer types for IL2CPP; device builds must verify actual platform filesystem/AOT behavior.

The host pairs each successful present-time monotonic settlement boundary with a UTC high-water timestamp. Saves capture that boundary without settling additional time. Player commands save immediately; rewards/HP/counter changes are checked every second; a periodic checkpoint runs at most 15 seconds between successful writes, plus pause and best-effort quit/destruction writes. Explicit debug resets switch to an unsaved sandbox and preserve the real player save. Save errors stop live ticking and block player interaction until a safe retry.

Startup/resume performs validation and one bounded offline settlement on a candidate session off the Unity thread. State, consumed UTC boundary and pending welcome report commit together **before** the shared runtime adopts the restored session. Only the existing host can adopt/rebase; this never calls settlement again. Scene/UI navigation does not reopen the store or calculate absence. The old session becomes unowned and unreachable from the live model; the same runtime/model retain navigation preferences. The host itself survives scene changes without retaining a previous scene's UI.

Away time is `max(0, utcNow - consumedUtcBoundary)`, eligible time is at most the existing four-hour cap. The domain advances over capped excess without simulating it, and the durable UTC cursor consumes the entire interval. Rollback retains the previous UTC high-water mark. All offline XP uses background rules (zero baseline; configured effects capped at 50%); items/loot still follow actual simulation. No 7-hour extension is granted. Pure loot rolls use the saved seed plus character/monster/drop IDs and saved kill index, so no mutable random cursor is lost. Local time is not a trusted anti-cheat authority.

Offline receipts are assembled in the same preflight batch as rewards and published only after successful domain commit. They attribute gross earned items and actual XP after the skill cap directly to each character/activity, not shared-bank net deltas. Combat death and single-job completion produce factual stop reasons. Absences of at least five minutes create one account-wide report; an undismissed report merges later eligible intervals with explicit multiple-visit labeling. Acknowledgment durably clears the report without awarding or advancing anything. A crash before disk commit replays from the old boundary; a crash after commit reloads the already-settled state and pending receipt. See `Stage8B06Verification.md` for recovery, schema and exact Windows checks.

Production inspection confirms **single job per Start**, including offline settlement. Existing code has no queue/automatic ingredient reservation for subsequent jobs. The user's report of a continuous-production iteration is not present at the starting reference; adding repetition requires a separate reviewed change, not an undocumented balancing/behavior expansion here.
