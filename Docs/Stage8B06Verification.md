## Save schema and domain coverage

`Application.persistentDataPath/Idlebound/player-v1.json` is a version-1 JSON envelope: `Version`, UTF-8 JSON `Payload`, SHA-256 `Sha256`. Payload holds `Catalog` fingerprint, consumed `UtcTicks`, validated `State`, nullable `Pending`. Save size is limited to 4 MiB. The hash is corruption detection, not anti-cheat/security encryption. No credentials, Unity objects or view references are saved.

`State` saves available slots, active ID, simulation ticks, equipment serial and pure loot seed, cancellation policy; each character's ID/name, all nine exact decimal XP/levels, HP, assignment ID, partial ticks, completion counter, reserved job recipe ID, encounter target/HP/clocks and scoped XP effects; shared bank stable IDs/quantities; equipped/banked instance IDs and item/owner IDs; per-character/monster kill counters. Production inputs are already consumed in inventory and represented by the pending job; restore never consumes or refunds them again. Source-catalog fingerprint protects recipe input definitions from silent changes.

Definitions/names, profiles, skill metadata, max HP, item slots and reservation ingredients are reconstructed. Enchantments/inherent equipment effects have no implemented powers; current instances have no permanent enchant identity. Implemented scoped background effects are persisted without introducing bonuses. No gold wallet or collection-log ownership system exists; owned loot stays in bank plus relevant kill counters. No new account economy is invented. UI tab/search/scroll state is intentionally not disk persistence; in-session Bank return remains unchanged.

Validation rejects unknown/duplicate references, roster/slot/skill/XP-level errors, negative quantities/progress, impossible clocks/HP, conflicting assignments, orphan jobs/encounters, duplicate or inconsistent instances, invalid bank-instance quantities, effects or report data. Failed restore constructs no live replacement. Future versions and catalog mismatches require migration/review; they do not fall back to old balance or guess missing definitions. Raw catalog/comment changes currently alter the conservative fingerprint as well.

## Atomic writes, backup and recovery

Writes serialize/preflight a detached document, flush `player-v1.json.tmp`, then use safe replacement preserving the previous primary as `player-v1.json.bak`. Initial creation also seeds a backup. Interrupted pre-commit writes leave prior primary/backup usable; temporary files never become committed rewards just because they exist. If only interrupted/orphaned evidence remains, loading blocks rather than silently starting fresh.

A corrupt primary with a valid, semantically compatible backup restores that backup, logs a developer warning and preserves the original as `.corrupt-<guid>` before publishing the recovered state. A corrupt backup encountered during writing is also preserved as evidence. Backup recovery can lose changes newer than that backup; it is not a promise of zero data loss after corruption. Unsupported future primary/backup versions are never overwritten. No valid recovery, inaccessible storage or catalog mismatch blocks play with Retry; no fresh starter state overwrites an existing unusable save.

Use **Idlebound → Local save → Reveal real save folder** in the Editor. On Windows the normal persistentDataPath is under `%USERPROFILE%\AppData\LocalLow\<CompanyName>\<ProductName>`, but use the actual revealed folder rather than assuming project settings. Back up the **entire Idlebound folder** before manual recovery. Stop Play/the app before moving files. Restore known-compatible files from your external backup, then retry. Do not edit timestamps, hashes or catalogs to bypass validation. Starting over is deliberately not an automatic error response: to deliberately test a first launch, move the whole existing folder to a safe backup location and restore it afterward.

The implementation flushes file contents and uses platform replacement APIs; actual Windows/mobile filesystem behavior and power-loss characteristics still require testing. If replacement is unavailable or fails, gameplay blocks safely instead of degrading to destructive overwrite. OS force-kill before the most recent checkpoint may lose unsaved online progress; last settled durable state remains recoverable.

## Autosave, lifecycle and clocks

The dedicated `GameSessionHost` survives scene reloads without carrying a scene's UI. It owns the same `SessionRuntime` and `GameUiModel`. Startup and resume validate/settle candidate state in a worker task while a responsive overlay blocks interaction. Only after state plus pending receipt are committed does the registered owner adopt the restored session and rebase the existing monotonic runtime. No second clock drives rewards. UI/navigation/rebuild never opens a save or triggers offline settlement.

Successful player commands save immediately at the last settled UTC boundary. The host checks reward/XP/HP/counter/equipment changes once per second and checkpoints at most every 15 seconds between successful writes; pause/focus loss and normal quit/destruction also save best-effort. Saving itself never calls settlement. Background entry first settles the online boundary, then saves. Background return settles once via `LocalGame` and rebases the runtime, avoiding the old runtime's independent offline replay. Duplicate pause/focus events are coalesced. Scene changes reuse the host; stopping/restarting Play mode uses the same disk rules as app restart.

UTC high-water policy: away = max(0, nowUTC − consumedUTC). Domain settlement receives the entire elapsed interval but simulates at most **4 hours**, consuming capped-out time in its durable clock/cursor. Rollback grants no time and does not lower the saved UTC boundary. Very large legitimate/implausible absences are capped. Purely local files/device clocks cannot prevent deliberate clock manipulation; no cloud time authority is implemented. Load/processing time itself is not additional simulated time. Save errors freeze ticking; retry saves the last live boundary before bounded offline catch-up, so errors cannot replay already-captured online progress.

Offline XP is background for **all** characters, including the selected character: baseline zero, explicit persisted effects only, 50% cap. Resources/items/loot follow existing deterministic rules despite zero XP. No 7-hour extension is invented. Gathering keeps partial cycles; production keeps reserved ingredients; death stops combat. Loot is pure in saved seed, character/monster/drop IDs and saved kill counter, not a mutable RNG stream. Exact decimal XP is serialized without float conversion.

**Production discrepancy:** inspected `StartProductionAt`/`SettleTo` still run exactly one job, remove its reservation on completion and do not auto-reserve another. Offline production also produces at most that job's output. Cancellation refunds only an unfinished job. Continuous production/queues are not present in the starting branch and were not silently implemented. Stop reason is “Job completed”, not an invented exhausted-materials condition.

## Welcome-back transaction

At least **5 minutes** away with positive eligible settlement creates one account-wide report. Below that, real offline progression is still saved without a popup. Receipts are built from actual preflight gathering/production/combat grants, keyed by character/activity, and commit with the corresponding state. Gross produced materials are not inferred from bank deltas. Actual XP is measured after the level-99 XP cap; zero-efficiency XP is not fabricated. Report includes duration, eligible duration, truncated-cap indication, assignments, item grants, skill XP and actual completion/death reasons.

Unacknowledged reports survive restart. Later eligible intervals merge into that same report and are explicitly labeled across visits; totals may exceed four hours across multiple separately capped absences. Continue first checkpoints current live state/boundary and then durably clears the pending ID. It never grants rewards. A failed acknowledgment retains the pending report. A crash before offline commit reloads the old state/boundary; after commit it reloads already-paid state and the same pending summary. Scene changes cannot re-award or acknowledge it. Live gameplay time resumes behind the report after offline commit.

## Remaining limitations / review decisions

Unity/phone/AOT/filesystem checks above remain mandatory. Saving is local-only, unencrypted and not cheat-proof; catalog migration is deliberately blocking rather than automatic. Recovery can roll back to an older backup. No continuous production, cloud sync, trusted server time, offline extension bonuses, economy or equipment powers are added. Async offline work assumes Android/iOS/desktop managed threads; WebGL is not a target. One-second meaningful-state polling plus periodic saves and best-effort lifecycle callbacks cannot guarantee the latest uncheckpointed frame survives abrupt power loss. Existing coarse prototype art remains. Raw catalog edits require a migration strategy before shipping frequent content updates. Do not run multiple app/Editor processes against the same save directory; cross-process synchronization is not implemented.
